## 结论

记忆子系统已从「整轮结束后批量写状态」演进为**事件溯源 + 事务提交**架构，算法层做了实质性修正。上一轮 5 项发现中 **4 项已修复**，1 项残留。

当前记忆算法可以概括为：**自定义启发式 SRS（版本号 `legacy-srs-v1`），以对数衰减控制稳定度增长，但不是 FSRS**；标准 FSRS v4 实现存在但仅作影子对比，不参与线上调度。需特别说明：代码中虽实现了 FSRS 幂律遗忘曲线与回忆概率校正，但该分支在生产路径上**不可达**（见 1.5），因此线上实际生效的只有**对数衰减增长 + 线性难度回归 + 间隔 `S/D`**。

主要遗留问题**不在算法公式本身**，而集中在四处：

1. **会话恢复闭环**——检查点写入与读取不对称，主路径的崩溃恢复实际不可达（4.1、4.2）。
2. **数据操作闭环**——用户主动导入进度缺少确认、校验与备份，桌面端非原子（4.6）。
3. **实现与设计背离**——「回忆概率校正」已实现但生产路径不可达，算法文档与线上行为不符（4.9）。
4. **规模边界**——批量查询未分块、非识别计划 N+1（4.3、4.4）。

此外 4.8 与 4.10 同属**维护期隐患**：4.8 是不可达的重复 `copyWith` 扩展；4.10 是 28 个零引用成员，以及多个「消费端在跑、触发端不存在」的半接线功能——后者已构成对 4.1 的独立印证。

算法层本身的数值行为已由探针实测确认是自洽的：质量分档位可达、间隔单调、上限生效、掌握判定要求跨日独立回忆（见 1.8）。唯一值得标定的是其**保守程度**（见 1.9）。

## 一、记忆算法实际实现

### 1.1 调用链

```
答题 → RecallCommitService.commitAttempt
        ├─ RecallEvaluator.evaluate        （证据 → 质量分）
        ├─ MemoryScheduler.schedule        （生产调度，legacy-srs-v1）
        │    └─ SrsAlgorithm.updateCardState
        └─ FsrsScheduler.schedule          （影子，只写 shadow 字段）
     → SqliteProgressRepository.commitRecall（单事务：事件 + 状态 + 首次接触）
```

- 生产入口：`lib/features/memory/domain/memory_scheduler.dart:15`
- 核心公式：`lib/domain/srs.dart`
- 影子调度：`lib/features/memory/domain/fsrs_scheduler.dart:57`
- 事务提交：`lib/data/sqlite/sqlite_progress_repository.dart:707`
- **注意**：`MemoryScheduler.schedule` 调用 `updateCardState` 时**未传 `recallProb`**，因此 `_adjustStabilityByRecall` 在生产路径恒不生效（详见 1.5 与 4.9）。

### 1.2 质量分 q ∈ {1,3,4,5}

`lib/domain/srs.dart:60`。答错/超时固定为 1；答对按反应时间分档：

- 快答阈值 `fast = 有基线 ? min(0.5T, 0.8B) : 0.5T`
- 慢答阈值 `slow = min(0.95T, max(0.8T, B·m))`，其中 `m = 0.8 + clamp((阈值倍数-1)/1.5, 0, 1)·0.6`
- 无历史基线时 `B = 0.6T`

代入默认倍数 1.5、无基线：`fast = 0.5T`，`slow = 0.8T`。即 `rt ≤ 0.5T → 5`、`rt ≥ 0.8T → 3`、其余 `4`。慢答阈值被钳制在时限内，**该档位可达**——这正是上一轮之后的关键修正。

评级映射（`recall_commit_service.dart:307`）：会话内重试或使用过提示的作答，正确一律降级为 `difficult`、错误记为 `forgot`，避免辅助回忆获得完整奖励。

### 1.3 难度 D

`lib/domain/srs.dart:190`。目标难度 `targetD = max(1.2, 3.0 − (q−1)·0.4)`，按 10% 步长做均值回归，钳制 `[1.2, 3.0]`。设计意图是避免「一次答错就大幅跳变」。

### 1.4 稳定度 S

`lib/domain/srs.dart:203`。

- 成功（q ≥ 3）：`S' = S · (1 + α(q−2) / (1 + 0.15·ln S))`
  - 分母为对数衰减因子，稳定度越高增长越慢
  - 会话内重测（`shortTermReview`）额外压制：增长项取 `min(0.065, growth·0.12)`
- 失败（q ≤ 2）：`S' = max(β, S · (0.20 + 0.10·min(1, S/30)))`
  - 高稳定度卡片保留更多痕迹，属渐进式惩罚

### 1.5 回忆概率校正（**生产路径不可达**）

`lib/domain/srs.dart:247`。遗忘曲线 `R = (1 + t/(9S))⁻¹`（幂律，非指数）。校正系数：

- 成功：`1 + (1−R)·0.3`（越逾期、奖励越大）
- 失败：`max(0.85, 1 − 0.15R)`
- 最终钳制 `[0.5, 120]`

**但这段逻辑在当前生产路径上不会执行。** `_adjustStabilityByRecall` 仅在传入 `recallProb` 时生效；`recallProb` 的唯一来源是 `estimateRecallProbability`，其唯一调用点在 `SrsAlgorithm.batchUpdateCardStates`（`srs.dart:329`）。而 `batchUpdateCardStates` 的唯一调用点是 `session_controller.dart:1062` 的 `_updateSrsStates`，后者只在 `!_recallCommitService.supportsReliableCommit` 时才走（`session_controller.dart:974`）。

`supportsReliableCommit` 取决于仓储是否实现 `ReviewCommitRepository`（`recall_commit_service.dart:42-58`），而 SQLite 与 Hive 两个仓储**都实现了**它，因此在现有全部平台上该条件恒为 true，`_updateSrsStates` 不可达。

结论：生产路径的稳定度更新**只由 1.4 的公式决定**（含对数衰减），幂律遗忘曲线与回忆概率校正实际未参与线上调度，目前仅保留在批量兼容路径与统计口径中。这也解释了 1.8 的实测轨迹为何与「不含校正」的算式完全吻合。若确实希望实现「越逾期、奖励越大」，需要让 `MemoryScheduler.schedule` 显式传入 `recallProb`。

### 1.6 间隔与到期

`lib/domain/srs.dart:227`。`I = round(γ·S''/D')`，钳制 `[1, maxIntervalDays=90]`。到期时间从**实际作答时刻**起算；若为会话内提前复测且原到期更晚，则保留原到期日，防止同日刷题把长期复习日期不断推后。

### 1.7 长期掌握判定

`lib/models/card_state.dart:95`：

```
isMastered = 手动标记「已认识」 OR (S ≥ 16 且 longTermReviews ≥ 2)
```

`longTermReviews` 的累加条件（`recall_models.dart:115`）相当严格，需同时满足：**独立回忆**（未揭示答案、未用提示）+ **非会话内重试** + **确实到期** + `q ≥ 3`。手动标记走独立 flag，不伪造跨日回忆，且下一次真实回忆会清除该 flag。

### 1.9 与 FSRS 影子调度的定量差异

`fsrs_scheduler.dart` 是**完整且正确**的 FSRS v4 参考实现（17 个固定参数，含初始稳定度、难度回归、成功/遗忘稳定度、可提取性）。其间隔公式为 `9S(1/r − 1)`（`fsrs_scheduler.dart:178-181`），取目标保持率 0.90 时恰好退化为 `round(S)`。

需要注意：影子调度器**会用自己的 FSRS 规则重算稳定度**，并不复用卡片上的 `legacy` 稳定度，因此两者的间隔差异不是单纯的 `D` 比值。实测（同一条到期复习证据、同一张卡片状态）：

| 起始 S | 生产间隔 | 影子间隔 | 影子/生产 |
|---|---|---|---|
| 2.0 | 1 天 | 4 天 | 4.00× |
| 4.0 | 2 天 | 6 天 | 3.00× |
| 10.0 | 6 天 | 12 天 | 2.00× |
| 20.0 | 12 天 | 22 天 | 1.83× |

即在低稳定度区间差距可达 **4 倍**，随稳定度上升收敛到约 **1.8 倍**——比早期报告所写的「1.2–3 倍」更宽，且趋势是**高稳定度时反而更接近**。结论方向不变：当前线上策略明显比 90% 目标保持率保守，这属于有意的校准选择，但值得在真实跨日样本上验证，而不是仅凭影子字段对比后直接切换。

## 四、本轮新发现（按优先级）

> **行号约定**：本节记录的是**审查时（修复前）**的发现，行号以修复前版本为准。由于 4.5 / 4.6 / 4.8 / 4.10 等项已落地修复，文件长度随之变化；凡引用已漂移的，均在行号旁标注「修复前 X / 修复后 Y」，已删除的代码标注「已删除」。§七（修复记录）与 §八（当前状态）的行号以**当前工作树**为准。

### 4.1 P1 崩溃恢复对「首页启动的会话」不可达

`test_screen.dart:71` 的恢复分支以 `settings.hasActiveSession` 为门槛，而 `hasActiveSession = currentSessionId != null && remainingWordIds.isNotEmpty`（`models/app_settings.dart:170-171`）。

问题在于 **`saveTestProgress()` 在全源码树中没有调用点**——`grep -rn "saveTestProgress"` 仅命中 `app_settings_notifier.dart:494` 的定义本身（连测试都没有调用）。唯一会写 `currentSessionId` 的是 `stageCustomSession()`，它只被疑难词页、摘要页、每日历史页和日历组件调用。

后果：
- **首页「开始学习」发起的普通会话**：`currentSessionId` 始终为 null → `hasActiveSession == false` → 进程被杀后重启时走 `startSession(widget.config)` 全新开始，**已保存的 `SessionCheckpoint`（主队列、延迟队列、答题记录）被读取后丢弃**。由于提交只发生在整轮结束（`_finishSession`），这些答题记录同时丢失。
- 同时 `stopSession()`（另一个会 `checkpointStore.clear()` 的路径）在生产代码中**也无调用点**（仅测试调用）。整轮正常完成时会在 `_finishSession` 清理检查点（`session_controller.dart:1004`），但**中途放弃的会话**其检查点会一直残留，因为 `_handleWillPop` 与 `dispose` 都只调用 `pauseSession()`。
- 反向问题：自定义会话被中途退出时，残留的 `currentSessionId` 会让**下一次首页会话误入恢复分支**，用旧会话的剩余词表覆盖新生成的今日计划。

即：文档所述「后台、退出和生命周期切换会保存检查点；恢复使用检查点配置」中，**保存成立，恢复对主路径不成立**。

**已复现**（见第二节）：快照记录了 `currentWordId=3`、2 条作答、`mainQueue=[4]`，首页式重启后 `attempts=0`、从第 1 题重新开始，检查点被完全丢弃。

建议：二选一——要么让首页/会话在启动时写入会话标记（恢复 `saveTestProgress` 调用），要么让 `test_screen` 直接以检查点是否存在且未完成作为恢复依据，不再依赖设置里的进度标记；同时明确退出页面时清理标记的时机。

### 4.2 P2 检查点恢复忽略 `status`，已作答题目会被重新开放

`SessionCheckpoint` 保存了 `status`（`session_checkpoint.dart:11,30`），但恢复路径未读取它，而是无条件设为 `SessionState.waiting`（`session_controller.dart:419`）。

可达路径：`pauseSession()` 允许在 `resolved` 状态调用（`session_controller.dart:1079`），而 `_resolveAttempt` 进入 `resolved` 后并不清空 `currentQuestion`（`session_controller.dart:492`）。因此**在 800ms 反馈窗口内切后台**会写出一个 `status='resolved'` 且已含该题 attempt 的快照。恢复时该题被当作未作答重新开放，用户再答一次会产生第二条 attempt（`kind = inSessionRetry`）。

影响有限但真实：重复事件会被提交，练习计数被抬高；因第二条按会话内重试处理（`countFailureAsLongTerm=false`），长期稳定度只被推进一次，故不会造成严重漂移。同理，若快照的 `millisLeft` 为 0，恢复后会立刻再次超时。

**已复现**（见第二节）：`status=resolved` 的快照恢复后进入 `waiting` 且保留原作答，再答一次即产生第二条 `inSessionRetry` 记录。

建议：恢复时按 `checkpoint.status` 分流——`resolved` 应恢复为反馈态并继续推进下一题，而不是重新开放作答。

### 4.3 P2 批量状态查询未分块，可能触发 SQLite 绑定参数上限

`getCardStates` 将全部 ID 拼成单个 `IN (?,?,…)` 并整体绑定，**没有任何分块**（**修复前** `sqlite_progress_repository.dart:503-517`；修复后已按 `_maxSqlVariables = 800` 分片，见 `:458`、`:461-475`）。

词库共 **3177 词**（A1 900 / A2 867 / B1 870 / B2 540）。调用点 `study_plan_service.dart:55` 会传入当前所选级别的**全部**词 ID：

- 默认仅选 A1（900）→ 未超限，故日常使用不易暴露。
- 一旦同时选中 A1+A2（1767）→ 超过 `SQLITE_MAX_VARIABLE_NUMBER = 999`（SQLite < 3.32，对应 Android 11 及更早系统自带的 SQLite）。
- 全选 4 个级别 → 3177 个绑定参数。

由于 `sqflite` 在 Android 上使用系统 SQLite，此路径在较旧设备上会直接抛「too many SQL variables」。`getWordStatuses`（同文件 704 行）有同样模式。

**参数计数已确认**（见第二节）：A1 单级 900（未超限，故日常不易暴露）、A1+A2 1767、全选 3177。未做 SQLite 实测，上限值 999 依据 SQLite < 3.32 的 `SQLITE_MAX_VARIABLE_NUMBER` 默认值。

建议：按 500–900 一批分块查询后合并，或改为一次性拉取全部卡片状态再在内存中过滤（`_allCardStates()` 已有实现）。

### 4.4 P2 非识别能力计划存在 N+1 查询

`study_plan_service.dart:69-75`（**修复前**）对每个候选词单独调用 `getLearningItemState(itemId)`，并用 `Future.wait` 一次性并发发出。按 A1 规模即 900 次查询，全选级别可达 3177 次并发查询堆积在单一 SQLite 连接上。修复后已改为一次 `getLearningItemStates()` 批量取回再在内存过滤（见 7.4）。

当前仅在 `skill != meaningRecognition`（即英文产出等）时触发，识别主路径不受影响；但这是产出练习打开即卡顿的直接来源。

建议：改为按 `lexeme_id` 批量查询（`getLearningItemStates(lexemeId:)` 已支持按词条查询）或新增批量接口。

### 4.6 P2 进度导入缺少确认、校验与备份，非 SQLite 平台存在数据丢失窗口

`settings_screen.dart:1821-1830` 的「导入进度」入口**没有任何确认对话框**，单击即执行；而破坏性更低的「清除测试记录」「清除答题记录」都配有确认弹窗（`_showClearTestRunsDialog` 等）。权限保护与破坏程度是倒挂的。

`_importProgress`（修复前 `settings_screen.dart:2587-2634`；修复后因新增校验与备份逻辑移至 `:2672` 起）的实际行为：

- **无 schema 校验**：仅 `jsonDecode` 后直接交给仓储，字段类型不符会在导入中途抛异常。
- **无导入前备份**：`LegacyProgressMigrator` 的备份只覆盖「旧库→SQLite」迁移路径，用户主动导入这条路没有备份。
- **固定文件名**：导入导出共用 `progress_export.json`（**修复前** `settings_screen.dart:2571` 导出、`:2603` 导入），无时间戳。Downloads 里的**任意旧快照**都会被静默导入并整体替换当前进度。（修复后导出改为带时间戳的 `progress_export_<stamp>.json`，见 `:2656`；导入改为列出全部快照由用户选择，见 `:2676-2678`。）

关键在于平台差异。`_useSqliteLearningCore()`（`base_providers.dart:26-36`）仅在 Android/iOS/macOS 返回 true；**Web、Windows、Linux 走 Hive**。两种仓储的导入原子性不同：

| 平台 | 仓储 | `importProgress` 行为 | 失败后果 |
|---|---|---|---|
| Android / iOS / macOS | SQLite | 全部删除与写入包在**单个事务**内（`sqlite_progress_repository.dart:1162-1163`） | 回滚，原数据完好 |
| Web / Windows / Linux | Hive | 先 `await clearAllProgress()`，再逐个 box 写入（**修复前** `hive_progress_repository.dart:952-959`），**无事务** | 修复前：数据已清空且仅部分恢复 |

因此在前者上，一个损坏的导出文件是安全的；在后者上，同一个文件会让用户**先看到数据被清空、再看到「导入失败」**，且不可恢复。桌面端（Windows/Linux）目前是这条路径的实际暴露面。

**已复现**（Hive 为纯 Dart 依赖，可在宿主机直接验证；见第二节输出）。探针先导入 3 张卡片状态 + 1 条测试记录，再用「`cardStates` 合法、`testRuns` 混入非法元素」的负载触发中途失败：原有 3 张卡片状态与 1 条测试记录**全部归零**，而新负载中排在失败点之前的卡片状态**已被写入**。即数据既未回滚、也未完整恢复——「已清空且仅部分恢复」得到实测证实，非静态推断。

建议：
1. 导入前弹确认对话框，明确提示「将覆盖当前全部学习进度」。
2. 导入前自动写一份当前数据的备份（复用 `LegacyProgressMigrator` 的备份目录约定）。
3. 导入前做 schema 校验（版本、必需字段、列表元素结构），校验不通过直接拒绝，不进入清空流程。
4. 让 Hive 的 `importProgress` 也具备回滚能力（先写入临时 box，成功后原子替换），或明确限制该平台不开放导入。
5. 导出文件名加时间戳，并让导入由用户选择文件，而非固定路径。

### 4.7 P3 迁移路径设计良好，值得作为参照

同一批代码里，`LegacyProgressMigrator`（`legacy_progress_migrator.dart`）的保护措施明显更完备，可作为上述导入流程的参照实现：

- 源库始终保留，只读不删（`migrate` 注释与实现一致）。
- 目标已有数据则跳过并记录 `skipped-target-has-data`，不覆盖（`hasCoreData` 还把 `word_preferences` 计入，避免只存了「暂不学习」就被判定为空库）。
- 迁移前写本地备份文件（`legacy-progress-<checksum>.json`）。
- 以去掉 `exportTime` 后的规范化 JSON 计算 SHA-256 作为幂等键，同一源不会重复迁移。
- 失败时记录 `failed` 状态并 `rethrow`，**不会被误写成 completed**，可用同一 checksum 重试。
- 导入本身在 SQLite 下是单事务。

### 4.8 P3 `SessionConfig` 存在第二个、不完整的 `copyWith` 扩展（当前不可达，属隐性陷阱）

`summary_screen.dart:734-767`（行号指**修复前**位置；该扩展**已按本节建议删除**，见 7.5）定义了一个 `extension SessionConfigCopyWith on SessionConfig`，其中同样提供 `copyWith`。但 `SessionConfig` 本身已在 `session_models.dart:132-174` 声明了同名的**实例方法**，且该实例方法会完整传递 `srsConfig`、`maxRetriesPerWord`、`maxTotalAttempts`、`cooldownWindow`、`plannedWordIds`。

Dart 的解析规则是**实例成员优先于扩展成员**，因此该扩展在任何调用点都不会被选中——全仓库对 `SessionConfigCopyWith` 的引用仅剩它自身的定义，属**不可达死代码**。

风险不在当下，而在后续维护：该扩展的字段清单比实例方法**少 5 项**（`srsConfig`、`maxRetriesPerWord`、`maxTotalAttempts`、`cooldownWindow`、`plannedWordIds`）。一旦有人删除或重命名实例方法，扩展会静默接管，`plannedWordIds` 随即退化为 `null`——而 `plannedWordIds == null` 会让 `session_controller.dart:338` 回退到旧的兼容选词逻辑，恰好绕开今日计划已确定的稳定顺序（这属于最难排查的一类回归）。同名的两份 `copyWith` 也提高了阅读时的误判概率。

建议：删除 `summary_screen.dart:734-767` 的扩展（该扩展**已删除**，见 7.5）；若确需以扩展形式提供，应转发到实例方法，而不是重新拼装字段。

### 4.9 P2 已实现的「回忆概率校正」在生产路径不可达，算法实际行为与设计意图不符

`srs.dart` 实现了完整的 FSRS 幂律遗忘曲线 `R = (1 + t/(9S))⁻¹` 及基于它的稳定度校正（成功时越逾期奖励越大、失败时惩罚设下界），文件注释明确标注为「P1 修复」。但调用链显示它**在线上不会执行**：

```
estimateRecallProbability   ← 唯一调用点 srs.dart:329
  └─ batchUpdateCardStates  ← 唯一调用点 session_controller.dart:1062
       └─ _updateSrsStates  ← 仅在 !supportsReliableCommit 时走 (session_controller.dart:974)
            └─ supportsReliableCommit = 仓储是否实现 ReviewCommitRepository
                 → Sqlite 与 Hive 两个仓储都实现 → 恒为 true → 不可达
```

生产路径为 `RecallCommitService.commitAttempt` → `MemoryScheduler.schedule`（`memory_scheduler.dart:22-29`），该调用**没有传入 `recallProb`**，因此 `_adjustStabilityByRecall` 直接原样返回。

影响：这不是数据损坏，而是**「已修复」的功能实际未生效**。风险有二：一是算法注释、文档与后续报告若据此描述线上行为会失真（本报告 1.5 已更正）；二是若有人依据「已实现逾期奖励」去标定参数或解释线上数据，会得到与预期不符的结论。

**已实测确认**：1.8 的实测轨迹与「不含校正」的算式逐项吻合（第 2 次 S=2.66、第 8 次 S=12.26）；若校正生效，这些数值会更高。

建议：二选一——要么让 `MemoryScheduler.schedule` 显式传入 `recallProb`（并补一条覆盖该行为的测试）以真正启用该特性；要么在 `srs.dart` 注明该分支当前仅服务于批量兼容路径，避免后续误读。

### 4.10 P3 存在成片的零引用成员，且多个功能属「半接线」状态

对 `lib/` 全树做了一次系统性引用扫描（判据：某标识符在 `lib/` 中**仅出现 1 次**，即除自身声明外零引用）。共 **72 个**成员命中。从中人工复核了 44 个（领域、会话、数据层，剔除主题与 UI 辅助方法）：**28 个完全零引用**（含测试也不引用），**16 个仅被测试引用**。

真正值得关注的不是数量，而是其中三个**功能半接线**的实例——它们的**消费端已实现，触发端却无调用点**：

**（1）会话进度持久化 API 整片无调用点（与 4.1 同源）**

`saveTestProgress`（修复前 `app_settings_notifier.dart:494`）、`updateTestProgress`（`:533`）、`resumeTestSession`（`:544`）三个方法均零引用（**三者已按 4.10 决策删除**）。这从 **API 层面独立印证了 4.1**：崩溃恢复失效的根因不是「恢复分支有 bug」，而是**写入侧从未被调用**——没有 `saveTestProgress`，`hasActiveSession` 就永远为 false，恢复分支自然不可达。

`skipCurrentQuestion`（修复前 `session_controller.dart:1132`）零引用（**已按 4.10 决策删除**）。注释表明其语义为「当作超时处理」，属面向用户的能力，但当前无任何界面调用。

建议：按功能意图逐个裁决——确定要保留的（如对外 API、算法公共入口）补上调用点或加注释说明；确定废弃的直接删除。优先处理上述三个「半接线」实例，因为它们是**用户可感知但实际无效**的功能。

### 4.11（已撤销）疑难词「自动暂停」曾疑为半接线，复核后不成立

**初判**：`LeechInterventionPolicy.plan()`（`leech_intervention.dart:38`）的 `suspend` 分支（`lapses >= 8`）产出的 `primaryAction` 在 `lib/` 中找不到消费方，怀疑界面向用户承诺了一个不会发生的自动暂停。

**复核结论：不成立。** 该初判只核对了**策略层**与**横幅渲染**，漏看了**同一屏的操作栏**：

- 横幅文案本身以「建议：」开头（`leech_words_screen.dart:618`），性质是**建议**而非承诺；其措辞「暂停自动安排并**等待人工处理**」明确指向人工操作。
- 同一屏的选择模式操作栏（`:209`–`:223`）提供「暂不学习」按钮 → `_suspendSelected()`（`:60`），正是把该建议落地的人工路径；该函数写入 `suspended: true`，并提示「已暂不学习，之后可在词库中恢复」。
- 消费侧 `study_plan_service.dart:110` 会跳过 `suspended` 词条，闭环成立。

因此这是「策略产出建议 → 界面展示建议 → 用户手动执行」的**完整闭环**，不是半接线。

**唯一残留**：`shouldPauseCard` 与 `availableActions` 两个便捷成员无消费方（仅被测试引用）。它们已归入 7.10 的「仅测试引用」清单，不再单列为缺陷。

**教训**：判定「半接线」时必须把**同一功能的所有交互入口**看完。本轮只顺着「策略 → 横幅」这条线查，漏了同屏的操作栏——而操作栏恰恰是让该功能成立的那一半。**「找不到消费方」不等于「功能不成立」，也可能只是我搜错了层。**

## 五、建议的处理顺序

1. **4.1**——恢复闭环不成立会让「崩溃不丢学习成果」这一核心承诺失效，且方向上是产品语义问题，应最先明确取舍。
2. **4.6**——导入无确认、无校验、无备份，且桌面端（Windows/Linux）非原子，存在用户主动操作导致整体数据丢失的路径；改动量小、收益明确。
3. **4.3 / 4.4**——真机性能与兼容性风险，属于发布前必须处理项（多级别选择即可触发）。
4. **4.2**——按 `status` 分流恢复，改动局部、风险低。
5. **4.5 / 4.8**——统一 `SessionConfig` 的构造方式，并删除 `summary_screen.dart` 中不可达的重复 `copyWith` 扩展。两者同源，都是「手工拼装 `SessionConfig` 丢字段」的变体，一并处理成本最低。
6. **4.9**——先明确「回忆概率校正」是要真正启用还是明确弃用：若启用，需让 `MemoryScheduler` 传入 `recallProb` 并补测试；若弃用，应在代码中标注，避免文档、注释与实现继续背离。
7. **算法标定**——生产间隔比 FSRS 影子保守 **1.83–4.00 倍**（低稳定度区间差距最大）、新词前 4 次复习间隔仅 1–2 天，建议在有真实跨日样本后统一标定，而非直接替换调度器。
8. **4.10**——对零引用成员逐个裁决。其中「会话进度持久化 API」应并入 4.1 一并处理；「疑难词手动标记」「跳过当前题」是用户可感知却实际无效的功能，建议优先补接线或明确移除。

## 六、值得保留的设计

- 幂等键 `sessionId:wordId:时间戳微秒:结果:选项` + `CardState.revision` 乐观并发 + `pending→committed` 写前日志与启动重放，构成完整的一次性提交语义。
- `ExposureEvent` 作为每日新词额度的**持久化**事实来源，使「提交后崩溃」不会重新开放当日额度。
- 能力维度（`LearningSkill`）与识别卡分离，产出/拼写不污染识别状态；技能级状态使用独立 `LearningItemState` 与独立 revision。
- 掌握判定要求跨日独立回忆而非仅稳定度阈值，避免「一个时段刷题即掌握」。
- 保留旧算法但用 `MemoryScheduler` 建立版本边界，使未来切换调度器不需要改动学习流程。
- `LegacyProgressMigrator` 的迁移保护（源库只读、目标非空跳过、checksum 幂等、失败不标完成、导入事务化）是仓库内最严谨的数据操作实现，可作为其他数据路径的参照。

### 7.1 4.1 崩溃恢复（P1）

**根因**：`test_screen.dart` 的恢复分支以 `settings.hasActiveSession` 为门槛，而该字段只由 `stageCustomSession` 写入——首页「开始学习」从不写它，导致进程被杀后已保存的检查点被读出却丢弃。

**改法**：把判据下沉到检查点本身。`SessionCheckpoint` 新增 `isResumable`（`status` 非 `finished` / `idle`，且队列或当前题非空），`_startSessionFromCheckpoint` 只要 `checkpoint.isResumable` 就恢复，不再依赖设置。

**顺带收尾整个「会话权威」集群**（否则旧口径会以别的形式继续误导）：

1. **统计页「当前会话」卡片**原先读 `settings.hasActiveSession`，同样漏报首页会话；且其进度来源 `settings.currentProgress` 的唯一更新入口 `updateTestProgress` 零调用，对自定义会话恒显示 0 进度。现改为读检查点，新增 `SessionCheckpoint.remainingQuestionCount` / `totalQuestionCount`（与 `SessionData.totalQuestions` 同口径），`learningStatsProvider` 的两个分支（正常与 catch 回退）都改用该口径。
2. **删除三个零引用 API**：`saveTestProgress`、`updateTestProgress`、`resumeTestSession`（后者是只打日志的空实现）。前两者正是 4.1 根因所依赖的「写入侧」——它们从未被调用，所以 `hasActiveSession` 永远为 false。
3. **删除两个误导性 getter**：`AppSettings.hasActiveSession` 与 `progressPercentage`。它们以 `currentSessionId` 判断会话存在性，口径本身不成立，留着还会被再次当作恢复门槛。字段本身（`currentSessionId` / `currentProgress` / `totalWords` / `remainingWordIds`）仍由 `stageCustomSession` 写入、`clearTestProgress` 清除，仅为兼容既有持久化数据而保留，已在模型内加注说明；彻底删除需要改持久化 schema，未在本轮执行。

**端到端证据**（`test/audit_fix_verification_test.dart` 新增用例）：从「首页式启动」→ 作答一题 → 反馈窗口内暂停（模拟进程被杀）→ 重启恢复，日志与断言确认：

```
=== Starting new session ===
Pausing session - current state: SessionState.resolved
=== Resuming existing session ===
Session ID: 3474b0da-...    Remaining word IDs: 4    Current progress: 1
Stopping session - current state: SessionState.resolved
```

即已答记录、会话 ID、当前题与反馈态全部保住，且恢复后不再重新开放已作答的题。

### 7.2 4.2 恢复时忽略 status（P2）

**根因**：恢复路径无条件把状态设为 `waiting`。若进程是在 800ms 反馈窗口内被杀，恢复后会把**已判分的题重新开放作答**，同一题被二次计入 `attempts` 并重复推进队列。

**改法**：按 `checkpoint.status` 分流——`resolved` 恢复到反馈态并继续推进下一题（`lastCorrect` 取自 `attempts.last`），其余保持原 `waiting` 并重启倒计时。

### 7.3 4.3 SQLite 绑定参数上限（P2）

`getCardStates` 原先把全部 ID 拼成单条 `IN (?,?,…)`。分块后实测：


3177 个 ID（全选四个级别）被拆成 4 次查询，每片均低于旧版 SQLite 的 999 上限。修复前是单条 3177 参数的语句，在 Android 7.0~11（SQLite < 3.32）上会直接抛 `too many SQL variables`。

### 7.4 4.4 N+1 查询（P2）

`study_plan_service.dart` 原先对每个词单独 `await getLearningItemState(itemId)`，A1 规模即 900 次、全选可达 3177 次。改为一次 `getLearningItemStates()` 后按 `itemId` 集合过滤。

### 7.10.1 扫描口径的修正与已知盲区（为什么数字会变）

「零引用」这个结论的可靠性完全取决于口径。本轮在这一点上修正了三次：

1. **人工子集 → 全量脚本**。原报告的 72 / 28 / 16 来自人工筛选的子集；全量脚本扫描得 1353 / 10 / 23。两组数字口径不同，不可比较（见 §二 的说明）。
2. **把注释与字符串纳入判定**。朴素计数会把**注释**和**字符串字面量**里的提及当成引用，从而**藏住真正的死代码**。实测：`DelayedReplayManager.maxRetries` 的唯一「测试引用」其实是测试名里的一句英文 `'... sessionRetryCount >= maxRetries (3)'`；`FsrsShadowResult.interval` 的两处「引用」是测试名里的 `intervals` / `interval` 单词。二者实为真死代码，已删除。
   - 但字符串**也不全是噪音**：`'${_two(m)}'`、`'$dailyNewWords'` 是 Dart 的真实可执行引用。一刀切掉字符串会反向误杀 6 个成员（`_fileStamp`、`_two`、`_formatHeaderDate`、`_getChosenAnswer`、`dailyNewWords`、`databaseFileName`）。
   - 因此脚本最终采用**四遍口径**：RAW → 去注释 → 去注释与字符串 → 去注释且字符串只保留插值表达式（判定口径）。`tool/deadcode_scan.py` 已入库，`python3 tool/deadcode_scan.py .` 可复现。
3. **已知盲区：区分不了「读」与「写」。** 当前判据只数出现次数，因此**只写不读**的成员会被算作「有引用」。实例：`LeechInterventionPlan.availableActions` 在 `lib/` 中出现 3 次（字段声明、构造参数 `required this.availableActions`、构造调用 `availableActions: List.unmodifiable(actions)`），全部是写入，**没有任何读取点**，唯一读取在测试里。
   - 要覆盖这一类，需要把判据从「出现次数」升级为「按上下文区分读/写」——例如排除 `this.<name>`、`<name>:`（命名参数）与 `Type <name>;`（字段声明）后，再看剩余出现次数是否为 0。本轮未做此升级，故此类成员靠人工核对补上，**不声称扫描已穷尽**。
4. **可达性分析的两处结构性误判（本轮修正，见 8.5）。** 为覆盖「互引死簇」而加入的第二遍 mark-sweep 起初给出 **427** 项，几乎全是误报；逐层定位后修掉两处结构性错误，收敛到 **24** 项：
   - **把调用点当成声明。** 方法模式的 `^\s{2,}返回类型 函数名(` 会把 `widget.progressColor ?? _getProgressColor(progress, themeStyle);` 解析成「返回类型 `widget.progressColor`、函数名 `_getProgressColor`」，于是**调用点自己生成了一条自引用区间**，可达性分析随即把真正被调用的成员判成死的。实测被误杀：`_getProgressColor`、`_two`、`_fileStamp`。修正为两条结构判据：**行首花括号深度 ≤ 1**（成员只在类体或顶层，方法体内的局部量在深度 ≥ 2）+ **语句边界**（只有紧跟在 `;` `{` `}` 之后的行才是声明起点，用于排除 `=>` 表达式体方法的续行）。
   - **把类当成框架入口。** 模式里的 `^\s*` 会**跨行吞掉换行**，使匹配起点落到上一行，于是

     ```
     @override
     Widget build(...) {...}
                          <- 空行被 \s* 吞掉，m.start() 落到这里
     class Foo {
     ```

     会把**前一个成员的 `@override` 算到 `class Foo` 头上**，把类误加进 roots，从而掩盖真正无人使用的类。修正为前导空白一律用 `[ \t]`。修正后 `FixedClock`（`core/clock.dart:16`）浮出水面——它此前正是被这个 bug 藏住的。
   - 收敛过程：`427 → 369`（把 `@override` 成员设为根）`→ 71`（修 `return _buildWordCard(` 被当成声明）`→ 33 → 25 → 24`（修上述两处）。每一步都用具体标识符的归属链取证，而非调参。

### 7.13 修复自身的回归：检查点判据的副作用（4.1 追加）

**这是本轮唯一一处「修复引入的缺陷」，在收尾核对时被捕获并已修复。**

**机制**：`_startSessionFromCheckpoint` 的恢复判据由 `settings.hasActiveSession` 改为 `checkpoint.isResumable` 后，恢复分支的数据来源也一并从 **AppSettings 字段**换成了**检查点**：

```dart
// 改前
if (settings.hasActiveSession) {
  startSession(sessionConfig,
    resumeSessionId: settings.currentSessionId,
    remainingWordIds: settings.remainingWordIds,   // ← 来源是 AppSettings
    currentProgress: settings.currentProgress,
    checkpoint: checkpoint?.sessionId == settings.currentSessionId ? checkpoint : null);
}
// 改后
if (checkpoint != null && checkpoint.isResumable) {
  startSession(sessionConfig,
    resumeSessionId: checkpoint.sessionId,
    remainingWordIds: checkpoint.mainQueueWordIds,  // ← 来源是检查点
    currentProgress: checkpoint.currentProgress,
    checkpoint: checkpoint);
}
```

而 `stageCustomSession()`（`app_settings_notifier.dart`）恰好**只写 AppSettings、不写检查点**。于是「日历/疑难词/错题 → 练习所选」这类显式编排入口，改前会走恢复分支但取用**刚编排进去的新词**（行为正确），改后则会被**残留的旧检查点顶掉**，用户新选的词被丢弃、恢复成上一轮会话。

**修复**：让 `stageCustomSession()` 承担「新会话使旧检查点失效」的语义——与 `clearTestProgress()` 共用同一个私有方法删除检查点 key：

```dart
Future<String> stageCustomSession(List<int> wordIds) async {
  ...
  await _discardSessionCheckpoint();   // 新增
  _debouncedSave();
  return sessionId;
}

Future<void> _discardSessionCheckpoint() async {
  final prefsAsync = _prefsAsync;
  if (prefsAsync is AsyncData<SharedPreferences>) {
    await prefsAsync.value.remove(SessionCheckpointStore.storageKey);
  }
}
```

同时把原先硬编码的 `'study_session_checkpoint_v1'` 改为引用 `SessionCheckpointStore.storageKey`，消除两处字面量各自维护的隐患。

**回归测试**：`test/review_fix_regression_test.dart` 新增用例「编排新会话时必须让旧检查点失效」——先写入一个可恢复检查点，调用 `stageCustomSession([9,8,7])`，断言 `AppSettings.remainingWordIds == [9,8,7]` **且** `SessionCheckpointStore.load() == null`。

**该测试已用「停用修复」的方式反证过确实能捕获缺陷**：临时注释掉 `_discardSessionCheckpoint()` 后运行，用例失败并输出

```
Expected: null
  Actual: <Instance of 'SessionCheckpoint'>
  TestScreen 以检查点判据决定恢复，编排新会话后旧检查点必须失效
```

恢复修复后全量 166 项通过。**一个从未失败过的回归测试，等于没有测试。**

**教训**：**改判据时，要连同追问「这个判据的数据来源是什么、旧来源还承担了什么副作用」。** 旧判据 `hasActiveSession` 读的是 `currentSessionId`，而该字段被 `stageCustomSession` 复用为「编排意图」的载体——它同时承担了「有没有会话」和「用户想练哪些词」两个语义。换判据时只看到前者，就会丢掉后者。这类「一个字段两种语义」的耦合，是判据迁移中最容易踩的坑。

### 7.14 交付前的引用复核（发现并修正 22 处漂移）

**为什么必须做**：修复会改变文件长度，而报告里的 `文件:行号` 是在不同时点写下的——§四 写于审查时（修复前），§七/§八 写于修复后。两者混在一份文档里，行号必然错位。读者按行号去查会看到无关代码，整份报告的可信度随之崩塌。

**做法**：写一个检查器，抽出报告中全部 `文件.dart:行号`，回读当前工作树，打印真实内容，并汇总「文件未找到 / 行号越界 / 文件名歧义」。本轮共解析 **104 条**引用。

**发现**：

| 类型 | 数量 | 实例 |
|---|---|---|
| **行号越界**（文件已缩短） | 3 | `summary_screen.dart:734/751`（行号指修复前位置；该扩展**已删除**，见 4.8 / 7.5） |
| **行号漂移**（指向无关代码） | 19 | `srs.dart:318` → 实为 `:329`；`session_controller.dart:1051` → 实为 `:1062`；`settings_screen.dart:2587-2634` → 实为 `:2672`；`sqlite_progress_repository.dart:1198-1199` → 实为 `:1162-1163`；`card_state.dart:103` → 实为 `:95` 等 |

**并且抓出一处跨章节自相矛盾**：§4.5 把 `summary_screen.dart:751`（修复前位置）列为「手工构造 `SessionConfig` 漏传 `srsConfig`」的实例，而 §4.8 认定同一区间 `734-767` 的扩展是**不可达死代码**。两节写于不同时点、彼此未对账。核实后确认：该处属死代码，**不构成实际风险**，§4.5 的该条已更正（真正在生产执行的是疑难词那三处）。

**处置**：为报告确立行号约定——§四 以修复前版本为准并标注「修复前 X / 修复后 Y」或「已删除」；§七/§八 以当前工作树为准。全部 22 处已按此修正，复核结果 **0 越界 / 0 缺失 / 0 歧义**。

**教训**：

1. **「逐条复核行号」不能靠肉眼**。22 处里有 19 处是「行号仍合法、但已指向别的代码」——只有把真实内容打印出来对照才能发现。越界的那 3 处反而是最容易看见的。
2. **修复完成后必须回扫自己写过的每一句引用**。修复是「文件的写操作」，会静默使所有旧行号失效；这一步与跑测试同等必要。
3. **同一份文档里混用两个时点的行号，必然产生矛盾**。要么统一到当前版本，要么显式分区并写明约定——本轮选了后者，并顺带发现了 §4.5 与 §4.8 的对账缺口。

**（5）仍然存在的盲区（本轮未解决，故不声称穷尽）**

1. **同名成员无法区分。** 扫描器按标识符名字归并，因此 `A.foo` 无人用、`B.foo` 有人用时，`A.foo` 会被漏报（假阴性）。上面 `correctionSuccessRate` 就是这类——两个声明必须靠人工拆开定性。反方向的假阳性不会由这条产生。
2. **区分不了「读」与「写」**（见 7.10.1 第 3 条），如 `availableActions`。
3. **写在方法体内的局部函数会被漏检**（本项目不存在此情况，属实现局限）。
4. 上述 24 项是「**生产**不可达」，不等于「应当删除」——第（3）(4) 组里多为组件库与预留 API，处置建议见 8.1–8.4。
